# 长列表性能与稳定性验证

日期：2026-11-21；基线 1.13.5，优化后 1.13.6。

## 结论

千本模拟中发现的主要开销是反复解码已有卡片、重绘未改变的操作控件、整表间距测量以及隐藏词表编辑器的重建。本轮采用局部缓存、失效更新、规则预索引与按需编辑器渲染，保留全部已加载卡片；不引入虚拟列表。

100／500／1000 本规模下，追加和返回操作均改善；千本仍可完整执行筛选、记录和导航。不同词表切换仍需处理全表，并非零耗时。数据清理未实施。

## 方法与边界

- Windows、Chrome/157.0.8103.79、1366 × 768，独立临时浏览器配置与实际扩展；所有页面、书籍接口、封面和账号接口均拦截为模拟响应。
- 1000 个测试词，模拟书目约一半命中；简介长度固定，包含封面、作者、字数和操作按钮。后台实际执行本地记录和配置写入。
- 规模测试先用种子批次建立 100／500／1000 本累积列表，再测真实 18 本增量；种子批次不是正常官网分页，不用于宣称线上首屏速度。
- 切换方案计时包含事件、扩展存储、规则应用及随后两次浏览器绘制回调。下面“启用原词表”是同一词表从关闭切到开启的两次均值，不能代替全新词表切换的耗时。
- 追加和返回是各规模单次观测；结果受设备、浏览器调度与缓存影响，不是性能 SLA，也不能据此承诺任意书量。
- 另做持续分页：从 18 本开始，每次 18 本，沿用生产代码的请求间隔，累计 56 页、1008 本。
- Headless 绘制回调间隔不等同显示器实际 FPS。原始 JSON 中的 DOM 计数包含浏览器保留的文档，仅用于诊断，不能据此判断内存泄漏；本轮未作内存下降比例声明。

## 测量结果

单位：毫秒；箭头为优化前 → 优化后。

| 累积书籍数 | 启用原词表 | 追加 18 本 | 从选书返回书库 |
| --- | --- | --- | --- |
| 100 | 78 → 30 | 59 → 23 | 54 → 23 |
| 500 | 208 → 43 | 187 → 21 | 365 → 67 |
| 1000 | 371 → 62 | 357 → 28 | 738 → 107 |

优化后切换到不同的 1000 词方案、再切回原方案：100 本 46／35 毫秒，500 本 93／119 毫秒，1000 本 157／210 毫秒。不同词表的测试是后补场景，没有对应的已归档基线，不作前后百分比比较。

各规模观察到的空闲长任务数均为 0。返回位置差均为 0 像素，累计列表节点和 URL 均保持一致；每次追加后的 ID 唯一数、隐藏计数及三列对齐均通过断言。

原始数据：[基线](长列表基线.json)、[优化后](长列表优化后.json)。重复运行结果写入 .local，正式报告是本次观测快照。

## 稳定性与数据验收

- 持续加载 1008 本：1008 个唯一 ID、504 本按规则隐藏，未出现重复。
- 千本列表模拟 HTTP 503：旧卡片不丢失，显式重试后追加成功，原有首卡片仍为同一节点。该场景先暂停自动加载，再注入手动请求失败，避免把自动调度与手动重试混为一次观测。
- 重新开启自动加载并返回连续全命中批次：三批后暂停；继续等待不再请求，仍可手动继续查找。
- 集成回归覆盖快速分类／排序切换、迟到响应丢弃、失败重试、无更多内容、关闭无限滚动回退及多标签页状态同步。
- 新增缓存回归：未变化卡片不重新解码；新增一张只解码该张；文本、简介、字体类和书籍链接变化后更新；复用卡片的按钮操作使用新书籍 ID。
- 匹配器等价性测试覆盖词序、重叠词、重复词、空词、标点、跨字段与 Unicode，含确定性随机样例。
- 原候选备注、自动屏蔽记录保留；现有候选导航、笔记、官方待看同步、失败重试和备份迁移回归继续执行。
- Chrome／Edge 独立导航和备份双向迁移通过。性能数字仅来自 Chrome，没有把它写成 Edge 的性能承诺。

## 复现

运行 npm run test:performance。需要本机 Chrome 和项目本地 devtools-runtime 中的 Chrome DevTools MCP／Puppeteer 运行库，条件与现有浏览器测试相同。临时浏览器使用模拟账号与模拟书目，不连接个人配置，也不调用真实官方书架写入。

功能回归运行 npm test，构建检查运行 npm run check，双浏览器迁移运行 npm run test:browsers。

## 后续范围

仍保留全部累积 DOM，规模进一步增长会增加资源占用。超过本次范围或低性能设备上若出现明显瓶颈，再依据实测评估分段渲染；本次不改变位置恢复策略，不增加数据清理，不接入 AI。
